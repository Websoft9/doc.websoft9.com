# Tech-Spec: doc.websoft9.com 项目文档、CI/CD 与 BMAD 工作流全面标准化

**Created:** 2026-03-04

## Overview

### Problem Statement

**文档层面**：项目根目录文档散乱，存在纯占位文件（`add_apps.md`、`docs/readme.md`）、内容错误混杂（文档原则/FAQ/技术配置堆在 `Notes.md` 一个文件）、关键信息缺失（`CHANGELOG.md` 空白、`developer.md` 单薄）。

**CI/CD 层面**：5 个 GitHub Actions 工作流大量使用过时 action 版本（`@v2`/`@master`），`check.yml` 全部功能被注释掉实际完全失效，`build_doc.yml` 遗留调试步骤且 Docker 代码缩进错误，均无 yarn/pip 缓存配置，缺乏 concurrency 控制，工作流存在业务逻辑盲区（未覆盖 PR 检查、无通知机制）。

**AI 辅助开发层面**：项目已引入 BMAD 方法但缺乏使用说明；新增 App 文档是项目核心高频任务，目前依赖模板脚本手工操作，缺少 AI 加速的标准化流程，导致文档质量不一致、新贡献者上手成本高。

### Solution

**文档**：删除无效占位文件；合并/重写根目录项目级文档为行业标准格式（README badge 规范、完整开发者手册、Keep a Changelog）。

**CI/CD**：全面升级 5 个 GitHub Actions 至最新 action 版本，从业务角度补充工作流缺失能力（PR 触发检查、通知机制），恢复 broken-links 检查，添加依赖缓存和 concurrency 控制。

**BMAD + App 文档流程**：在项目 developer 文档中说明 BMAD Quick Flow 的具体用法；设计并实现基于 Quick Flow 的新 App 文档创建标准化流程（模板 + Prompt + 步骤规范），让贡献者用 AI 快速生成高质量 App 文档。

### Technical Decisions

**CI/CD 技术决策：**
1. **yarn cache key**：使用 `${{ hashFiles('**/package.json') }}` 作为缓存键（`yarn.lock` 不提交，用 `package.json` 替代）
2. **concurrency**：按 `${{ github.workflow }}-${{ github.ref }}` 分组，`cancel-in-progress: true`，避免堆积
3. **broken-links 工具**：选用 `lychee-action@v2`（行业主流，速度快，支持排除规则，无需额外安装）
4. **lychee 配置方式**：使用根目录 `.lycheeignore` 文件管理排除规则（比 workflow inline args 更易维护，Task 10 需同时新建此文件）。必须排除的 pattern：
   - `localhost` / `127.0.0.1` — 本地开发地址
   - `libs.websoft9.com` — CDN 图片域名（外网请求不稳定，大量图片链接）
   - `NA4GDUSQ4H` — Algolia appId（出现在动态 URL 中）
   - `support-websoft9` — Algolia indexName
   - `support.websoft9.com` — 内部支持站点
   - `example.com` / 占位链接 — 文档模板占位
5. **pip cache**：使用 `actions/setup-python@v5` 内置 `cache: 'pip'` 参数，最简洁
6. **README badge**：引用 `build_doc.yml` 和 `check.yml` 的 GitHub Actions badge
7. **Keep a Changelog**：版本格式 `[Unreleased]` 作为初始占位，按 Added/Changed/Fixed 分类

**CI/CD 业务级审阅与优化建议：**

| 工作流 | 现状业务问题 | 优化建议 | 优先级 |
|--------|-------------|----------|--------|
| `build_doc.yml` | main 和 dev 分支共用同一 job，无法区分环境行为 | 用 `if: github.ref == 'refs/heads/main'` 区分生产部署步骤；dev 分支只 build 不 deploy | 高 |
| `build_doc.yml` | openapi.json 从 Docker 拉取，失败会阻断整个文档发布 | 将 apidocs 步骤改为 `continue-on-error: true`，文档发布不依赖 API 服务可用性 | 高 |
| `build_doc.yml` | 无构建失败通知 | 添加 `if: failure()` step，通过 GitHub issue 或 webhook 通知 | 中 |
| `check.yml` | 仅在 push 触发，PR 提交时不检查 | 增加 `pull_request` 触发，保护 dev 分支质量门禁 | 高 |
| `check.yml` | 功能全部注释，实际是空工作流 | 恢复 broken-links 检查，作为 PR 合并前的强制质量门 | 高 |
| `app_from_contentful.yml` | 仅 `workflow_dispatch` 手动触发，无自动化 | 可增加 `schedule` 定时触发（如每日凌晨同步 Contentful 内容变更） | 低 |
| `app_from_contentful.yml` | 失败时无通知，自动提交失败无感知 | 在 `git-auto-commit-action` 后增加失败通知步骤 | 中 |
| `json2md.yml` | `repository_dispatch` 事件名 `applist_dev_event` 无文档说明 | 在 workflow 注释中说明触发方`（由 websoft9 主仓库 release 时触发）` | 低 |
| `json2md.yml` | 从 `artifact.websoft9.com` 下载 zip，无校验机制 | 可增加文件完整性校验（hash check）或重试逻辑 | 低 |
| `update.yml` | 直接创建 PR，无测试验证 | PR 创建后触发 build 验证，避免升级破坏构建 | 中 |

**BMAD 使用文档设计决策：**
8. **文档位置**：作为 `developer.md` 中的章节，而非独立文件或 `develop/` 目录下的文件
   - `develop/` 是多项目公共贡献区，BMAD 是本仓库专属内部工具，放入会产生误导
   - 根目录 `developer.md` = 本仓库开发者手册，是正确归属
9. **面向读者**：本仓库的内容贡献者和文档维护者（非最终用户），使用中文
10. **BMAD 说明范围**：聚焦 Quick Flow（Barry）而非完整 BMAD 流程，降低上手门槛

**App 文档创建流程设计决策：**
11. **双轨并行**：保留现有 `template/create_app.py` 脚本（生成骨架文件）；新增 Quick Flow Prompt 模板（AI 填充内容）
12. **App 文档结构约定**（来自现有文件分析）：
    - `versioned_docs/version-2.0/apps/{appname}.md` — 主文档（入门指南 + 最佳实践 + 故障排除）
    - `versioned_docs/version-2.0/apps/_include/{appname}.md` — Meta 片段（由 Contentful 自动生成，不手工维护）
    - 中英文同步：zh 主文档 + `i18n/en/docusaurus-plugin-content-docs/version-2.0/apps/{appname}.md`
13. **Quick Flow 介入点**：在骨架文件生成后，用 QD 模式填充「入门指南」、「最佳实践」、「配置选项」、「故障排除」内容
14. **Prompt 模板格式**：Markdown front-matter + 结构化指令，存放于 `template/docs/zh/app.md`
15. **`_include` 前置依赖说明（方案 A）**：
    - `_include/{appname}.md` 由 `app_from_contentful.yml` 从 Contentful CMS 生成，**需要仓库 Write 权限 + CONTENTFUL_ACCESS_TOKEN**
    - 贡献者（外部/低权限）**无法自行触发**该 workflow
    - 职责分工：
      ```
      管理员职责（前置）：
        1. 在 Contentful 录入新 App 数据
        2. 手动触发 app_from_contentful.yml
        3. 确认 _include/{appname}.md 已 commit 到 dev 分支

      贡献者职责（管理员完成后）：
        1. git pull dev
        2. create_app.py 生成主文档骨架
        3. QD 填充内容
        4. 本地 build 验证（_include 已存在，不会报错）
        5. 提 PR 到 dev
      ```
    - DEVELOPMENT.md 中必须明确说明此前置条件，否则贡献者本地 build 失败无从排查
    - **不采用** placeholder 脚本方案（增加维护复杂度，方案 A 已足够清晰）

16. **DEVELOPMENT.md 中 BMAD Mermaid 流程图规格**：使用 `graph LR` 布局，三节点线性流程。节点定义：
    ```
    QS["QS 规格阶段\n(Barry Quick Spec)"]
    QD["QD 开发阶段\n(Barry Quick Dev)"]
    CR["CR 审查阶段\n(Code Review / Human)"]
    ```
    边定义：`QS -->|生成 tech-spec| QD`，`QD -->|实现 Tasks| CR`。图下方附一段文字说明各阶段核心产出（QS 产出 tech-spec 文件；QD 产出实现代码/文档；CR 产出 PR 审查 + merge）。
